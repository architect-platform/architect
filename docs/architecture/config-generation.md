# Configuration Generation Strategy

## Overview

Architect follows a **"generate where possible, hand-maintain where necessary"** approach to
configuration management. This document is the authoritative reference for which configuration
files are generated and which are hand-maintained across the repository.

The guiding principle: if a config can be derived from `architect.yml` declarations and
standardized templates, it should be generated. Hand-maintained configs exist only when
generation would sacrifice important flexibility or when no plugin yet covers that domain.

---

## Generated Configurations

### CI/CD Workflow Wrappers (13 files)

All module-level CI pipelines in `.github/workflows/` are generated by
`.github/scripts/gen_workflows.py`. Each generated file is a thin **~23-line wrapper** that
delegates to a reusable workflow template.

- **Header marker**: every generated file begins with `# This file is generated by Architect`
- **Drift detection**: `workflow-drift-check.yml` validates that generated workflows match
  their templates on every PR
- **Templates used**:
    - `classic-java-17.yml` — full pipeline with release/publish steps
    - `classic-java-17-no-release.yml` — build-only variant (no release)
- **Regenerate all workflows**:

```bash
python3 .github/scripts/gen_workflows.py
```

### Module `architect.yml` Files (32 files)

Each module declares its plugins and configuration in an `architect.yml` at its root.
These follow standardized patterns:

- **Kotlin modules** typically use: `gradle-architected` + `github-architected` +
  `docs-architected`
- Plugin declarations drive downstream generation (CI wrappers, docs aggregation, etc.)

## Hand-Maintained Configurations

Each hand-maintained config includes a rationale explaining why it cannot (yet) be generated.

### `mkdocs.yml` — HAND-MAINTAINED

**Reason**: The `docs-architected` generator lacks support for several features this repo
requires:

- Monorepo plugin (`!include` syntax for component docs)
- Custom nav structure (~120 entries with specific ordering)
- Light/dark mode palette toggling
- Several `pymdownx` markdown extensions

Full generation parity would require ~15 hours of plugin development.

**What `docs-architected` DOES handle**: auto-discovery of components, theme basics, and
standard extensions.

**Future**: When `docs-architected` supports the monorepo plugin and custom nav structures,
this file can be migrated to full generation.

### `detekt.yml` — HAND-MAINTAINED

**Reason**: Static analysis rules are cross-cutting policy decisions. No architect plugin
currently generates detekt configurations.

**Location**: Root `detekt.yml`, consumed by all Kotlin modules via Gradle convention plugins.

### Reusable CI Workflows (2 files) — HAND-MAINTAINED

| File | Purpose |
|------|---------|
| `reusable-kotlin-pipeline.yml` | Core CI policy with release/publish steps |
| `reusable-kotlin-no-release-pipeline.yml` | Build-only variant (no release) |

**Reason**: These define the actual CI policy (JDK version, caching strategy, Architect task
sequence). The thin generated wrappers delegate all real logic here.

### Release & Security Workflows (7 files) — HAND-MAINTAINED

| File | Purpose |
|------|---------|
| `dependency-vulnerability-scan.yml` | Repo-wide Trivy + npm audit |
| `docker-image.yml` | Docker image build and push to GHCR |
| `linux-packages.yml` | `.deb`/`.rpm` package builds |
| `native-image.yml` | GraalVM native image compilation |
| `update-homebrew.yml` | Homebrew formula update on release |
| `windows-installer.yml` | Windows MSI installer build |
| `workflow-drift-check.yml` | Validates generated workflows match templates |

**Reason**: Each workflow contains unique, complex logic specific to its purpose that does
not fit a templated generation model.

### Gradle Build Files — HAND-MAINTAINED

- `build.gradle.kts` per module
- `gradle/libs.versions.toml` (version catalog)
- Convention plugins in `gradle/`

**Reason**: No architect plugin generates Gradle build files. The `gradle-architected` plugin
executes existing Gradle builds but does not produce them.

## Generation Capabilities by Plugin

| Plugin | Generates | Does NOT Generate |
|--------|-----------|-------------------|
| `docs-architected` | `mkdocs.yml` (basic), component aggregation | Full nav structure, monorepo plugin config |
| `github-architected` | CI workflow wrappers from templates | Reusable workflows, release workflows |
| `gradle-architected` | *(none — executes builds)* | `build.gradle.kts` |
| `scripts-architected` | *(none — executes scripts)* | Script files |
| `pipelines-architected` | *(none — orchestrates tasks)* | Pipeline definitions |

## Adding a New Module's CI

1. Add an entry to `.github/scripts/gen_workflows.py`
2. Run `python3 .github/scripts/gen_workflows.py`
3. Commit the generated workflow file
4. **Alternative**: run `architect github-init-pipelines` (generates from `architect.yml`)

## Future Generation Opportunities

- **Multi-language pipeline templates** — Python, Go, Node.js CI wrappers
- **`.editorconfig` generation** — derive from `architect.yml` code-style config
- **Dockerfile generation** — derive from `architect.yml` deployment config
- **Full `mkdocs.yml` generation** — requires `docs-architected` enhancement for monorepo
  plugin and custom nav support
